## The defect, as observed

The .ipa produced by run 32691034648 (head ee43181e, the 0.2.32 commit) carries:

    CFBundleIdentifier         top.vansin.agentnetwork
    CFBundleShortVersionString 0.2.32
    CFBundleVersion            1        <-- run_number was 13

## Why it looked wired and was not

- `app.json` pins `expo.ios.buildNumber: "1"`, so `expo prebuild` writes the
  literal `1` into the generated `Info.plist`.
- The archive step passes `CURRENT_PROJECT_VERSION="$IOS_BUILD_NUMBER"`. A build
  setting can only reach the plist if the plist references it; this one stores a
  literal, so there is nothing to expand. The setting is accepted and ignored.
- `INFOPLIST_KEY_CFBundleVersion` would be the same class of no-op: those
  settings apply only when Xcode generates the plist
  (`GENERATE_INFOPLIST_FILE=YES`), and Expo ships a real `INFOPLIST_FILE`.
- The run number *did* reach the artifact name (`agent-network-ios-ipa-13`),
  which is what made the wiring look correct from the outside.

Nothing fails at build time. App Store Connect rejects a reused
`CFBundleVersion`, so the error surfaces on the first upload following another
build with the same number — which is exactly where the 0.2.32 TestFlight run
was headed.

## Change

1. A step after `expo prebuild` writes `$IOS_BUILD_NUMBER` into the generated
   `Info.plist` with PlistBuddy (excluding `Pods/`), reads the value back, and
   fails closed if the plist is missing or the read-back disagrees.
2. The existing `Verify archive uses App Store distribution signing` step now
   also reads `CFBundleVersion` from the **archived app** and exits 1 with an
   `::error::` when it differs from `IOS_BUILD_NUMBER`.
3. `CURRENT_PROJECT_VERSION` is kept — it is consistent with the Xcode side, it
   is simply no longer the only thing standing between us and a rejected upload.

The archive assertion is the load-bearing half. Injection happens ten steps
before the archive; a pod install or a plist regeneration in between could undo
it with no error at all. The only value that matters is the one inside the app
that was actually archived.

## Not verified here

That the fix produces `CFBundleVersion=13…` in a real archive. That needs a
macOS runner and the signing environment, which this change deliberately does
not trigger. What the container can prove is that both mechanisms are wired and
that removing either is caught — and the archive assertion means the next real
run cannot ship a wrong build number silently: it will fail the build instead of
failing an upload weeks later.
