## The defect

ChatScreen fetches a conversation by recipient:

    fetchTasks(cfg, { to_name: alias, limit })

`to_name` constrains who received a task and says nothing about who sent it.
Any node on the network can dispatch to that alias. The renderer nonetheless
labelled every message with the viewer's identity:

    <Text …>{currentUsername}</Text>
    <AliasAvatar alias={currentUsername} size={36} />

`currentUsername` comes from GET /api/auth/me and has no relationship to the
message. A dispatch sent by 通信牛 therefore rendered as something the viewer
had written — reported from desktop v0.2.30 with a screenshot.

## Why the data was already there

- `tasks.from_name` is `TEXT NOT NULL DEFAULT 'hub'` (server/src/db.ts) and
  GET /api/tasks returns the full row, so the field is always present.
- server/src/rest-identity.ts `resolveRestFromSession` decides it:
  user-token client -> `requested || authenticatedUsername || "api"`;
  node token -> the node's own alias, and a node claiming another name is
  refused with 403 rather than silently relabelled.
- The client type already declared `from_name?: string` (src/api.ts).

So a non-empty `from_name` that is neither this client's username nor the
legacy `api` label is genuinely another sender.

## The change

`src/chat-sender.ts` — `senderLabelFor(item, currentUsername)`:
falls back to the viewer for a missing/blank/non-string `from_name` (optimistic
local echoes have none yet), for the viewer's own username, and for the legacy
`api` label; otherwise returns the sender's alias, trimmed. `hub` is treated as
a real distinct sender, because a hub broadcast is not the viewer's message.
`ChatScreen.tsx` uses it for both the author line and the avatar. Bubble
placement is unchanged — only the attribution.

## Not verified here

The fix is asserted at unit and source level, not against a live hub — that
would mean pointing a client at production. What a live check would add: that
`from_name` on real rows matches the alias a human recognises. The hub schema
(NOT NULL) and the identity resolver make an empty or spoofed value the
excluded case, and an unexpected value degrades to showing that value rather
than to showing the wrong person.
