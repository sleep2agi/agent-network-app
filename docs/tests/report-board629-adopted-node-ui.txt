disabled restart with Stop then Start guidance, readable pending/error states.
Do not infer authority from hostname or node id. Verify current Hub protocol
before exposing adoption. Existing created-node behavior must be preserved.

Validation planned: ck-style model/API/source guards; Docker browser tests with
in-page Hub stubs only, desktop 1200x800 and mobile 390x844 screenshots.
No real Hub/node operations, no version change, no merge or release.

Implementation: Hub .110 managed/adoption and adopt_capable reads; header user
credentials, explicit network/target/request scope. Public request_adopt_node,
stop_node and start_node tools only. No discovery (separate board #654).
Missing managed/adoption fields: no new controls and no new queries, no error.
Created nodes keep existing controls; adopted controls replace the old danger
buttons and refuse restart locally. Stop/start require confirmation. Adoption
explains no process restart and requires an explicitly chosen capable daemon
and operator-supplied workspace. Hub/daemon remain authoritative for permission,
same-machine identity and allowed roots. No hostname-based client authority.

Request acceptance is pending, not success. Request-specific polling checks kind,
request id and target node, bounds waits, maps failures including timeout to
readable translated copy. Unknown error text is never rendered. Components are
keyed by Hub/account/network/node; stale responses cannot write to a new target.
