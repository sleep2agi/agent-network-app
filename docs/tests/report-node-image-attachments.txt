Issue #173 — authenticated node image attachments
=================================================

Source commit under test
------------------------
063826b5f26e3b5380d7364ced9a607337354edc

Root cause
----------
Both the main workspace and detached chat window render ChatScreen. The node-reply
dialect shown in #173 uses two plain-text lines (`图片 file_id: ...` and
`取回: GET /api/files/... (需 Bearer)`). The old parser noticed only the bare API
path, discarded its image type, assigned a generic filename, and therefore selected
the generic file row instead of an authenticated image preview. The internal fetch
instruction also remained visible as message text. Structured task attachments are
available in meta_json, but the reply column remains plain text, so both paths need
support.

Scope and overlap check
-----------------------
Every open PR and every changedFiles page was fetched without a result limit before
editing. PR #133 changes connectivity files, #68 changes api.ts and sender tests,
and #52 changes App.tsx and several profile/storage files. None intersects this
change's ChatScreen, attachment display/download, web image, or attachment tests.
api.ts was intentionally left untouched.

What changed
------------
* Parse structured meta_json attachments and the legacy node `图片 file_id` reply,
  including pure-image, text-plus-image, and multiple-image messages.
* Remove internal server paths and Bearer-fetch instructions from displayed text.
* Render authenticated thumbnails with explicit preview, original-file download,
  actionable authentication/network errors, and click-to-retry on web and native.
* Reuse ChatScreen so the main workspace and detached chat have the same behavior.
* Namespace native cache files by an opaque Hub/profile authentication scope. The
  raw server URL and token never enter filenames, DOM URLs, or the browser download
  manager; legacy unscoped cache entries are purged by a schema bump.
* Sniff PNG/JPEG/GIF/WebP bytes when a legacy server returns octet-stream without a
  useful filename.

Revision 2 — close an already-open viewer at the auth boundary
--------------------------------------------------------------
Source commit under test:
29016d69dc4bf4960c4533364e18551c31573dd3

Independent review found that the thumbnail children cleared their own pixels when
credentials changed, but the parent ChatScreen retained `viewerUri`. Consequently an
already-open Tauri `blob:` URL or native `file:` URI could remain visible after moving
to another conversation, profile, or Hub. ChatScreen now derives a viewer scope from
the conversation key plus the opaque authentication cache scope and closes the modal
whenever that combined scope changes. The wiring test independently pins both producers:
AuthedWebThumb's blob preview and AuthedThumb's native file preview.

The cache-scope comment was also narrowed: the 64-bit value is best-effort high-entropy
isolation bookkeeping, not a cryptographic digest or a claim that collision is
impossible. No new dependency was introduced.
