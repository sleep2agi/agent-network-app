Problem reproduced
------------------
ChatScreen called sendTask without a priority and api.ts omitted priority from
POST /api/task. Hub therefore applied its default "normal" priority to every
Desktop message, even though the Hub schema and dequeue order support high.

Implemented contract
--------------------
- Desktop and mobile composers expose an explicit "priority send" control.
- sendTask always transmits an explicit high/normal priority.
- The chosen priority is recorded before the network attempt and survives
  failure, restart restoration, and retry. Old persisted rows without the new
  field remain normal.
- After submission the composer resets to normal, preventing accidental
  priority inheritance by later messages.
- This is queue priority, not a claim that an in-progress Codex turn was
  interrupted. True TUI steering remains a runtime capability boundary.
